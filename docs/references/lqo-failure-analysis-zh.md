# 学习型查询优化器的失败原因分析：Bao、Neo、Lero 为何难以落地

**报告日期：** 2026-05-06  
**背景：** 基于最新研究文献的批判性分析

---

## 执行摘要

尽管 Bao (SIGMOD 2021)、Neo (VLDB 2019) 和 Lero (VLDB 2023) 在学术论文中展示了令人印象深刻的性能提升，但这些学习型查询优化器（Learned Query Optimizers, LQOs）在生产环境中的部署极为罕见。最新研究揭示了一个残酷的事实：**在严格的机器学习评估标准下，大多数 LQO 甚至无法稳定超越 PostgreSQL 的传统优化器**。

本报告基于 2024-2026 年的最新研究，深入分析这些优化器失败的根本原因。

---

## 一、核心问题：理想化假设与生产现实的鸿沟

### 1.1 阿里巴巴 MaxCompute 的教训

阿里巴巴在 2026 年发表的论文 [Learned Query Optimizer in Alibaba MaxCompute](https://arxiv.org/abs/2602.07336) 直言不讳地指出：

> "现有学习型查询优化器由于理想化的建模假设和设计选择，仍然不适合现代分布式、多租户数据仓库。"

**四大生产环境挑战：**

1. **高度动态的执行环境**
   - 分布式系统中计划代价的巨大方差使训练数据不可靠
   - 同一个查询在不同时间执行的代价可能相差数倍
   - 网络延迟、资源竞争、多租户干扰导致代价预测失效

2. **统计信息缺失**
   - 许多查询缺少传统优化器依赖的统计元数据
   - 新表、临时表、外部数据源往往没有统计信息
   - LQO 的特征工程严重依赖这些统计信息

3. **模型更新不可行**
   - 在生产规模下持续重新训练会中断服务
   - 传统的"收集数据 → 重新训练 → 部署"循环太慢
   - 无法快速适应工作负载变化

4. **收益不确定**
   - 优化收益无法均匀地转移到不同的查询模式和项目
   - 某些工作负载受益显著，其他工作负载可能性能下降
   - 难以预测哪些场景值得部署 LQO

## 二、机器学习视角的系统性问题

### 2.1 违反 ML 基本原则

2023 年的研究 [Is Your Learned Query Optimizer Behaving As You Expect?](https://arxiv.org/html/2309.01551v2) 从机器学习角度对 LQO 进行了严格评估，发现了惊人的结果：

> "PostgreSQL 在不同的训练/测试划分上优于大多数 LQO。"

**关键发现：**

1. **推理时间主导问题**
   - LEON 在 JOB 查询上花费 9.6 小时进行推理
   - 即使查询执行时间有所改善，推理开销也会抵消所有收益
   - 实际端到端延迟反而更差

2. **训练效率悖论**
   - Balsa 训练 40-85 小时，性能反而不如训练 2 小时的 Bao
   - 过度的计划探索并未带来相应的质量提升
   - 训练时间与性能不成正比

3. **数据生成问题**
   - PostgreSQL 的动态优化意味着强制执行的查询计划可能不会按预期执行
   - 训练数据被污染，标签不准确
   - 模型学习到的是错误的代价模型

### 2.2 编码问题：违反不变性原则

**致命缺陷：** 仅使用基数值进行编码违反了不变性原则。

- 不同的过滤器产生相同的基数会创建一对多映射
- 模型无法区分语义不同但基数相同的查询
- 导致预测混乱和性能不稳定

**示例：**
```sql
-- 这两个查询基数相同，但代价可能完全不同
SELECT * FROM users WHERE age > 30;  -- 基数: 10000
SELECT * FROM users WHERE name LIKE '%smith%';  -- 基数: 10000
```

### 2.3 协变量偏移（Covariate Shift）

当数据库内容变化时，LQO 性能显著下降：

- Bao 的编码在缩减数据集上训练时，某些查询出现 **24 倍的性能下降**
- 模型对训练数据分布过度拟合
- 泛化能力极差

### 2.4 测试集偏差

不同的数据划分策略导致结果差异巨大：

- "Base Query Sampling"（最现实）：LQO 表现远差于简单划分
- 学术论文倾向于选择对自己有利的划分方式
- 结果不可复现，无法公平比较

## 三、灾难性遗忘与动态环境

### 3.1 静态假设的破产

[LIMAO 论文](https://arxiv.org/html/2507.00188) 指出 LQO 的核心局限：

> "现有 LQO 在静态查询假设下运行，使其在处理复杂、动态的查询环境时无效。"

**问题表现：**

1. **灾难性遗忘**
   - 适应新工作负载时，先前学习的知识丢失
   - 性能在工作负载转换期间不稳定
   - 无法保留对旧查询模式的优化能力

2. **重新训练成本**
   - 面对重大环境变化时需要从头开始完全重新训练
   - 计算成本高昂
   - 知识丢失严重

3. **性能波动**
   - 没有适当的机制，LQO 随时间产生不一致的计划质量
   - 生产环境无法容忍这种不稳定性

## 四、合成数据集与真实工作负载的鸿沟

### 4.1 LinkedIn 的真实评估

[LinkedIn 的研究](https://arxiv.org/html/2504.17181v1) 揭示了合成数据集（如 TPC-H、JOB）与生产环境的巨大差距：

**数据复杂性差异：**
- LinkedIn 的 Trino 系统每天处理 **超过 100 万个查询**
- 涉及 **数万张表**
- 查询延迟范围从 **秒级到数天**
- TPC-H 只有 8 张表，22 个查询模板

**信息可用性限制：**
- 生产环境中"表的行数等基本信息有时不可用"
- Trino 的虚拟化架构导致统计信息缺失
- 合成数据集通常包含完整的统计信息，掩盖了这一现实挑战

**环境噪声：**
- 真实数据包含噪声：简单查询可能因网络延迟、外部系统响应延迟而执行时间长
- 合成数据通常不包含此类环境变量
- 模型在干净数据上训练，在噪声数据上失效

**编码信息丧失：**
- 相同编码可能对应不同的性能指标
- 这为模型精度设置了理论下界
- 无论模型多复杂，都无法突破这个上限

## 五、具体优化器的失败分析

### 5.1 Neo 的失败

**理论问题：**
1. **完全替代的风险**
   - 丢弃数十年的优化器工程积累
   - 对未见过的查询模式脆弱
   - 需要海量训练数据

2. **强化学习的挑战**
   - 动作空间巨大（所有可能的执行计划）
   - 探索效率低下
   - 收敛速度慢

3. **引导启动的局限**
   - 从 PostgreSQL 引导意味着继承其偏差
   - 难以学习到真正新颖的策略
   - 受限于初始优化器的质量

**实证结果：**
- 在严格的 ML 评估下，Neo 无法稳定超越 PostgreSQL
- 推理时间过长
- 对数据分布变化敏感

### 5.2 Bao 的失败

**理论问题：**
1. **提示依赖**
   - 依赖数据库暴露的优化提示
   - 提示空间有限，无法表达所有优化策略
   - 不同数据库的提示系统差异大

2. **Thompson 采样的局限**
   - 需要足够的探索才能收敛
   - 在高维提示空间中探索效率低
   - 对奖励信号的噪声敏感

3. **编码问题**
   - 树卷积神经网络的编码在协变量偏移下表现差
   - 24 倍性能下降的案例表明泛化能力不足

**实证结果：**
- 虽然学习速度快，但在某些查询上性能严重下降
- 对数据分布变化极其敏感
- 在真实生产环境中收益不稳定

### 5.3 Lero 的失败

**理论问题：**
1. **成对比较的局限**
   - 需要生成大量计划对进行训练
   - 计划生成本身就是昂贵的操作
   - 训练数据收集成本高

2. **排序 vs 绝对质量**
   - 只能判断相对好坏，无法判断绝对质量
   - 如果所有候选计划都很差，排序也无济于事
   - 依赖候选计划生成器的质量

3. **静态训练**
   - 批量训练，无法在线适应
   - 工作负载变化时需要重新收集数据和训练
   - 部署周期长

**实证结果：**
- 虽然声称在 PostgreSQL 上减少 70% 执行时间
- 但在更严格的评估下，收益不稳定
- 对新查询模式的泛化能力存疑

## 六、根本原因总结

### 6.1 理论层面

| 问题类别 | 具体表现 | 影响的优化器 |
|---------|---------|-------------|
| **过拟合** | 对训练数据分布过度拟合，泛化能力差 | Neo, Bao, Lero |
| **协变量偏移** | 数据分布变化时性能严重下降 | Bao (24×), Neo |
| **灾难性遗忘** | 学习新模式时忘记旧知识 | Neo, Lero |
| **编码缺陷** | 违反不变性原则，信息丧失 | Bao, Neo |
| **推理开销** | 推理时间过长，抵消执行收益 | Neo, LEON |
| **训练效率** | 训练时间与性能不成正比 | Neo, Balsa |

### 6.2 工程层面

| 问题类别 | 具体表现 | 生产环境影响 |
|---------|---------|-------------|
| **动态环境** | 代价方差大，预测不可靠 | 训练数据污染 |
| **统计缺失** | 缺少关键元数据 | 特征工程失效 |
| **模型更新** | 重新训练成本高，周期长 | 无法快速适应 |
| **收益不确定** | 某些工作负载受益，其他下降 | 部署风险高 |
| **环境噪声** | 网络延迟、资源竞争 | 标签噪声大 |
| **多租户干扰** | 资源竞争不可预测 | 代价模型失效 |

### 6.3 评估层面

| 问题类别 | 具体表现 | 后果 |
|---------|---------|------|
| **合成数据偏差** | TPC-H 不代表真实工作负载 | 结果不可信 |
| **测试集选择** | 有利的划分方式夸大性能 | 无法复现 |
| **缺乏标准** | 没有统一的评估框架 | 无法公平比较 |
| **忽略推理时间** | 只报告执行时间，不报告推理开销 | 误导性结论 |
| **忽略尾部延迟** | 只报告平均性能，忽略最坏情况 | 生产不可接受 |

## 七、为什么生产部署如此罕见？

### 7.1 微软的谨慎做法

[微软的论文](https://arxiv.org/abs/2210.13625) 揭示了即使是资源丰富的大公司也采取极其谨慎的策略：

**QQ-advisor 的设计选择：**
- **外部化查询规划器**：将优化工作移到大规模离线管道
- **避免在线修改**：不直接修改实时优化器
- **工作负载特化**：为特定工作负载实例专门化优化，而非通用方案

**关键洞察：**
> "现代分析工作负载高度异构且极其复杂，使得通用查询优化器对许多客户和场景不可行。"

这表明即使是微软也不信任 LQO 能够作为通用解决方案。

### 7.2 生产部署的三大障碍

1. **风险不可接受**
   - 性能回归可能导致严重的业务影响
   - 不稳定性在生产环境中不可容忍
   - 传统优化器虽然不完美，但至少可预测

2. **投入产出比不划算**
   - 训练和维护成本高
   - 收益不确定且不稳定
   - 传统优化器的改进可能更划算

3. **技术债务**
   - 引入复杂的 ML 系统增加维护负担
   - 需要 ML 专家和 DBA 的跨领域合作
   - 调试和故障排除困难

## 八、成功案例的启示

### 8.1 阿里巴巴 LOAM 的突破

LOAM 通过**生产优先的重新设计**实现了真正的生产部署：

**关键创新：**

1. **无统计编码**
   - 从算子语义和执行历史推断数据分布
   - 不依赖传统统计信息
   - 适应统计缺失的现实

2. **环境感知建模**
   - 显式捕获执行上下文如何影响计划代价
   - 处理动态环境的方差
   - 鲁棒性显著提升

3. **领域适应**
   - 无需传统重新训练即可泛化到未见查询模式
   - 快速适应新工作负载
   - 避免灾难性遗忘

4. **项目选择**
   - 优先部署高影响力的场景
   - 避免收益不确定的风险
   - 渐进式推广

**结果：**
- 生产工作负载上 **CPU 成本节省高达 30%**
- 真正的生产部署，而非实验室结果

### 8.2 成功的关键要素

对比 LOAM 与 Bao/Neo/Lero，成功的关键在于：

| 要素 | Bao/Neo/Lero | LOAM |
|------|--------------|------|
| **设计出发点** | 学术理想化假设 | 生产现实约束 |
| **统计依赖** | 严重依赖 | 无统计编码 |
| **环境建模** | 忽略动态性 | 显式环境感知 |
| **适应机制** | 重新训练 | 领域适应 |
| **部署策略** | 全面替代 | 选择性部署 |
| **评估标准** | 合成数据集 | 真实生产工作负载 |

## 九、对 ADL-OPT 的警示

### 9.1 避免重蹈覆辙

基于 Bao、Neo、Lero 的失败教训，ADL-OPT 应该：

**不要做：**
1. ❌ 在 TPC-H 上取得好结果就认为成功
2. ❌ 忽略推理时间开销
3. ❌ 假设统计信息总是可用
4. ❌ 假设执行环境是静态的
5. ❌ 使用简单的基数编码
6. ❌ 追求完全替代传统优化器
7. ❌ 忽略协变量偏移和泛化能力
8. ❌ 只报告平均性能，忽略尾部延迟

**应该做：**
1. ✅ 在真实 DuckDB 工作负载上评估
2. ✅ 测量端到端延迟（包括推理时间）
3. ✅ 设计无统计或统计缺失鲁棒的方法
4. ✅ 显式建模执行环境的动态性
5. ✅ 使用丰富的嵌入而非单一值
6. ✅ 增强而非替代现有优化器
7. ✅ 严格测试泛化能力和协变量偏移
8. ✅ 报告最坏情况和方差

### 9.2 推荐的保守路径

**阶段 1：离线数据收集（当前 v0）**
- 专注于高质量的标签收集
- 使用 DuckDB profiling 获取真实代价
- 收集多样化的工作负载
- 记录执行环境信息

**阶段 2：离线分析工具**
- 不要急于在线部署
- 先做离线的计划分析和建议
- 让 DBA 人工审核建议
- 积累信任和经验

**阶段 3：保守的在线辅助**
- 如果必须在线部署，从最保守的方式开始
- 只在高置信度时提供建议
- 保留传统优化器作为后备
- 严格监控性能回归

**阶段 4：渐进式推广**
- 从特定工作负载开始
- 逐步扩大覆盖范围
- 持续监控和调整
- 准备好随时回滚

## 十、结论

### 10.1 残酷的现实

Bao、Neo 和 Lero 在学术论文中展示了令人印象深刻的结果，但它们在生产环境中的失败揭示了一个深刻的真相：

> **查询优化是一个比学术界想象的更加复杂、更加依赖上下文、更加难以用纯数据驱动方法解决的问题。**

### 10.2 失败的根本原因

1. **理想化假设与现实的鸿沟**
   - 静态环境假设 vs 动态生产环境
   - 完整统计信息假设 vs 统计缺失现实
   - 干净数据假设 vs 噪声数据现实

2. **机器学习基本原则的违反**
   - 过拟合、协变量偏移、灾难性遗忘
   - 编码缺陷、信息丧失
   - 训练/测试分布不匹配

3. **工程现实的忽视**
   - 推理时间开销
   - 模型更新成本
   - 多租户干扰
   - 尾部延迟

### 10.3 未来方向

学习型查询优化器不是死路，但需要根本性的重新思考：

1. **生产优先设计**（如 LOAM）
   - 从生产约束出发，而非学术理想
   - 显式处理动态性、噪声、统计缺失

2. **增强而非替代**
   - 保留传统优化器的智慧
   - ML 作为辅助而非主导

3. **严格的评估标准**
   - 真实工作负载
   - 端到端延迟
   - 泛化能力
   - 尾部性能

4. **保守的部署策略**
   - 离线分析先行
   - 选择性部署
   - 持续监控
   - 快速回滚能力

### 10.4 最后的警示

对于 ADL-OPT 和任何新的学习型优化器项目：

> **不要被学术论文中的漂亮数字所迷惑。在你能够在真实生产工作负载上、在严格的 ML 评估标准下、在考虑所有开销的情况下，稳定地超越传统优化器之前，不要声称成功。**

Bao、Neo 和 Lero 的失败不是它们的耻辱，而是整个领域的宝贵教训。
